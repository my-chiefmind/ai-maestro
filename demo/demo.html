You're the Maestro

You have the ideas. A team of robot coders does the typing — one small job at a time, and you check every single one.

Here's the whole plan

Three moves. That's it. Everything below is just those three moves, slowly.

💬

1. You describe it

You answer a few questions about the thing you want to make. Short answers are fine.

🗂️

2. It makes a plan

Your idea gets chopped into small jobs, in the order they should be built. You approve it.

🔨

3. It builds, you check

One small job per turn. You look at the result before the next one starts. You're in charge.

📖
Word check — "the board". Your project's to-do list. Big goals are called epics (like "make the pieces fall"), and each small job is a ticket (like "make the left arrow key move the piece"). Robots work tickets, one at a time.

2

Describe your ideaEight questions about your idea, then one about the board. Every one has an escape hatch.

This is the important bit — it's you telling the robots what you actually want. Answer in normal words. Nothing here is permanent.

↩️

3

Ask for a planOne command. Nothing gets built yet.

Open the AI tool in your project folder:

terminal 
claude

Then type this and press Enter:

claude code 
> /project-plan

Now the robots read your answers and turn them into a to-do list:

🏔️

3–6 epics

The big goals. For Tetris: get it on screen → make it playable → make it fun.

🎫

5–15 tickets

The small jobs inside those goals, each one small enough to check in a few minutes.

🔗

An order

Some jobs must wait for others. You can't clear a line before pieces can fall.

🛑
It stops here on purpose. No code gets written yet. Planning ends with the plan on your screen and a question: is this right? That pause is yours.
4

Be the bossRead the plan. Change what you don't like.

This is the most Maestro-ish moment of the whole thing. Read it like you're checking someone else's homework.

Want changes? Just say them in normal words:

claude code 
> Change the plan: add a ticket for sound effects, split the
  movement job into "move left and right" and "rotate", and
  don't build anything yet.

Happy with it? Make a save point:

terminal 
git add .
git commit -m "chore: initialize project with AI Maestro plan"
💾
Word check — "commit". A save point, exactly like in a game. Git remembers this moment forever, so you can always come back to it if a later change goes wrong.
5

Build it, one job at a timeThe command you'll use over and over.

claude code 
> /orchestrator

Here's what happens behind the curtain. Each ticket names its own robot pipeline, so a tiny job may skip the planner while a bigger one uses the full team:

#What the robot team does
1Picks the most important job that isn't waiting on another one.
2Copies your project into a safe sandbox, so your real files can't break.
3Runs the ticket's robot pipeline in order — often a planner first, then the right builder.
4The required review robots check the work, like teachers marking it.
5If it passes, the work joins your real project. If not, it stops and tells you why.
🏖️
Word check — "worktree". That safe sandbox: a separate copy of your project where a robot can make a mess without touching the version you care about. Nothing joins your real project until it passes the check.
🤖

I do one job per turn, then stop and wait. That's not me being slow — it's your turn to look. Type /orchestrator again for the next one.

🔁
Now repeat. Look at what changed, then run it again. Job by job, your idea turns into a real thing you can open and play.

Copy my homework: a Tetris clone

Stuck on what to type at Level 2? Use these answers exactly, and you'll be building Tetris.

answers for a Tetris clone 
Project name: tetris-clone
Product outcome: A browser Tetris game with a score, levels,
  pause, restart, and a game-over screen.
Primary users: Players on laptops and phones.
Stack: Plain JavaScript, HTML and CSS, drawing on a canvas.
  No extra tools.
Constraints: Keep the game rules separate from the drawing
  code; work with both keyboard and touch; store nothing about players.
How it should run locally: npx serve
How it should be tested: Node's built-in test runner for the
  game rules, plus a quick play-test in the browser.
Areas of work: frontend, docs

A plan for that usually comes out looking like this:

Epic (big goal)Tickets (small jobs), in order
Get it on screenthe empty game box → drawing the grid
Make it playablethe 7 piece shapes → moving and rotating → falling, landing, clearing lines
Make it funscore and levels → pause, restart, game over, phone controls

When something goes wrong

It will. That's normal, and none of it breaks your computer.

You see…What to do
command not found: npxNode.js isn't installed yet. Go back to Level 0.
command not found: gitInstall Git, then try the same line again.
It says idleEvery job is waiting on another job. Say: "nothing can start — fix the order in the plan".
It says blockedA robot hit a real problem and stopped instead of guessing. Read the reason — that's the honest answer, not a failure.
The board page won't openIn your terminal: cd maestro then npm run board, and visit localhost:5273.
You changed your mind about the ideaJust say so in the AI tool: "add a rule: it must work on a phone". Your brief gets updated.
🦸
You can always ask. The robots read plain English. "I don't understand what blocked means" is a perfectly good thing to type.
