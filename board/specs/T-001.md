# T-001 — `maestro update` destroys user content in `board/`

**Filed:** 2026-08-08 · **Epic:** e1 (Kit integrity) · **Severity:** P0, data loss, reproducible

Filed from lense-kit as `kit-096` after the incident there, and moved onto this board 2026-08-08
along with the rest of the package work. The bug is in this repo (`bin/cli.mjs`); so is the fix.

> **T-005 is a SECOND destroyer of this same directory**, found while moving this ticket here:
> `test/cockpit-server.test.mjs:75` `rmSync(SPECS, { recursive: true })` wipes the real
> `board/specs/` on every `npm test`. This ticket's own `testCmd` is `npm test` — so running
> this ticket's gate deletes this file. **Land T-005 first.**

## What happened

`maestro update` — the command added in ai-maestro `0.1.22` (commit `23f48e9`, "cli: add 'update' —
bring an installed kit to a new release") — was run against lense-kit on 2026-08-08 at ~15:01. It
vendored the kit into `maestro/` as designed, and in the same pass deleted:

| Path | Loss |
|---|---|
| `maestro/board/specs/` | 47 files — kit-033…kit-090, gs-001…gs-008, risk assessments, `.sql`, `.html` |
| `maestro/board/reports/` | 7 files |
| `maestro/board/README.md` | overwritten with the generic starter README |

All 54 were git-tracked, so recovery was a single `git checkout --`. **An untracked or uncommitted
board would have lost them outright** — which is the actual severity of this bug, not the recovery cost.

## Cause

`refreshVendoredKit()` — `ai-maestro/bin/cli.mjs:88-105`. The `board/` branch:

```js
const BOARD_USER_FILES = new Set(["data.json", "archive.json"]);   // cli.mjs:52

if (entry === "board") {
  const destBoard = join(dest, "board");
  mkdirSync(destBoard, { recursive: true });
  for (const f of readdirSync(destBoard)) {
    if (BOARD_USER_FILES.has(f) || VENDOR_SKIP.has(f) || existsSync(join(src, f))) continue;
    rmSync(join(destBoard, f), { recursive: true, force: true });   // ← line 98, the kill
  }
  ...
}
```

The function's own comment states the intent: *"Each entry is removed before copying so files deleted
upstream disappear too — a plain overwrite would leave them behind forever."* For `agents/`, `skills/`,
`render/` etc. that inference is sound: the kit owns those directories completely, so *not upstream*
does mean *deleted upstream*.

**`board/` is different — it is a user workspace, not a kit-owned directory.** `specs/` and `reports/`
were never shipped by the kit, so they fail the `existsSync(join(src, f))` test, are absent from
`BOARD_USER_FILES`, and get `rmSync`'d as though upstream had removed them.

`README.md` is a second, milder instance of the same defect via the *copy* loop (lines 100-104): it
exists upstream and is not a `BOARD_USER_FILE`, so a repo's hand-written board README is silently
replaced by the starter every update.

The kit contradicts itself here: the starter README that this very run installed documents `specs/`
as a board folder —

> **`specs/`** — one file per ticket that needs more than its `desc`: `specs/<ticket-id>.md`.

— so the kit *knows* `specs/` is user content. `BOARD_USER_FILES` just doesn't say so.

## Reproduce

**Do not attempt this with `setup` in a scratch directory.** `maestro setup` ignores `cwd`
(T-004 §2d) — an attempt on 2026-08-08 from a `/tmp` scratch dir instead scaffolded into
`~/source/` itself: it ran `git init` there, wrote `~/source/{.claude/,CLAUDE.md,.maestro.lock}`,
and dropped `config.json` + `context.md` into `~/source/ai-maestro/`. All of it was removed and
`~/source/ai-maestro` verified clean, but the two bugs compound: the one that scaffolds in the
wrong place feeds the one that deletes user content.

The lense-kit incident is itself the reproduction, and the code path is unambiguous — `board/`
entries not in `BOARD_USER_FILES` and not present upstream are unconditionally `rmSync`'d. Reproduce
only inside a directory whose parent chain contains no repo you care about, and verify with
`git init` + a commit first so recovery is a `git checkout` away.

## Fix

**Stop-the-bleeding (one line, correct but incomplete):**

```js
const BOARD_USER_FILES = new Set(["data.json", "archive.json", "specs", "reports"]);
```

This rescues today's two known casualties and leaves the faulty inference in place — the next
user-created board folder (`evidence/`, `templates/`, anything) hits the same rm.

**Correct fix — derive the removal set from the lock, not from absence.** `.maestro.lock` already
records every file the kit vendored (`files` map, keyed by path). Remove only paths the *previous*
lock listed and the *new* release no longer ships. Anything the lock never recorded is by definition
user content and must never be touched. That also removes the need for `BOARD_USER_FILES` to be
maintained by hand as a denylist-of-exceptions, which is the structural reason this bug exists.

**Additionally:** treat `board/README.md` as user-owned once it diverges from the shipped copy —
write the starter only when the file is absent, or when its hash matches the previously-vendored one.

## Containment until fixed

**Do not run `maestro update` in any repo whose `board/` holds `specs/` or `reports/`.** That is
lense-kit and every separated product (`~/source/{agrolense,applicify,babooly,mychiefmind,speclense,speaklense}`).
Use `setup` into a scratch dir and diff, or bump the dependency and re-render, until this lands.

## Recovery performed (2026-08-08)

```bash
git checkout -- maestro/board/specs maestro/board/reports maestro/board/README.md
```

47 + 7 files restored; board README restored to lense-kit's own. `node maestro/scripts/validate-board.mjs
maestro/board/data.json` → valid.

## Loose ends

- **Version skew.** `.maestro.lock` records `kitVersion: 0.1.22`; `node_modules/@mychiefmind/ai-maestro`
  is still `0.1.21`; the vendored `maestro/` copy is `0.1.22`. Three copies, two versions. Settle which
  one is authoritative for this repo as part of landing the fix.
- **Vendored tree is gitignored** (this ticket): `maestro/{agents,bin,cockpit,docs,render,scripts,skills,starters,LICENSE,package.json,README.md,VERSION}`
  plus `maestro/board/board.schema.json`. `maestro/{config.json,context.md}` and `maestro/board/{data.json,archive.json,specs,reports,README.md}`
  stay tracked — they are this repo's content, not the kit's.
- **Related:** T-004 (upstreaming toolkit capability) touches the same vendoring path. Land this
  first regardless of sequencing — it is the smallest change on the board and it is losing
  people's data in the meantime. T-005 is the same invariant violated in the test suite.
